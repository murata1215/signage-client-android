# Android アプリ OTA自動アップデート仕様書

signage-client-android (v1.70) で実運用中の自動アップデート機構を、別アプリへ移植するための仕様書。
APK配信サーバーは既存の signage-server を流用する前提。

---

## 1. 全体フロー

```
[アプリ側 常駐サービス]
  起動10秒後 + 以降60秒間隔
    ↓
  GET /api/player/update/check?key={client_key}
    ↓ JSONレスポンス
  サーバーの version_code > 自分の versionCode ?
    ├─ NO  → 何もしない（DL済みAPKがあれば削除）
    └─ YES → GET /api/player/update/download?key={client_key}
              ↓ APKバイナリを filesDir/updates/ に保存
            ACTION_VIEW Intent でAndroidインストーラー起動
              ↓ 確認画面（白い画面）が表示される
            インストール完了 →「開く」タップでアプリ再起動
```

- インストール方式は **ACTION_VIEW Intent方式** が実運用実績あり。
  PackageInstaller Session API によるサイレント更新も可能だが、非Device Owner端末では
  アプリが即killされ復帰画面が出ない問題があったため**未使用**（§7に補足）。
- 更新チェックの失敗（圏外・サーバー停止等）は致命的でないため握りつぶしてリトライ継続。

---

## 2. サーバーAPI契約（既存サーバー流用）

### ⚠️ 最重要: 別アプリ用にAPKスロットを分けること

現行エンドポイントは **signage用APKを返す**。別アプリがそのまま叩くと
**サイネージアプリがインストールされてしまう**（versionCode比較も別系列なので誤発火する）。

別アプリで流用する場合、サーバー側にいずれかの対応が必要：

- **案1（推奨）**: `app` パラメータ追加
  `GET /api/player/update/check?key=...&app={app_id}`
  サーバーは `uploads/{app_id}/version.json` と `uploads/{app_id}/xxx.apk` を返す
- **案2**: アプリ別エンドポイント
  `GET /api/player/update2/check` のように別パスを切る

> サーバー担当への依頼文テンプレは §9 参照。

### 2.1 アップデートチェック

```
GET {serverUrl}/api/player/update/check?key={client_key}
```

**レスポンス (200 OK, application/json):**
```json
{
  "version_code": 70,
  "version_name": "1.70",
  "url": "/api/player/update/download",
  "force": false
}
```

| フィールド | 型 | 説明 |
|-----------|-----|------|
| `version_code` | number | APKのversionCode（整数・単調増加） |
| `version_name` | string | 表示用バージョン名（例: "1.70"） |
| `url` | string | APKダウンロードパス。相対パス / 絶対URL / key付きフルパスの3形式に対応（§3.2参照） |
| `force` | boolean | 強制アップデートフラグ（予約。クライアント側は現状未参照） |

- 更新がない場合: 現在と同じ `version_code` を返せばよい（クライアントが `<=` 比較でスキップ）
- 認証: 他のPlayer APIと同じ `?key={client_key}` クエリパラメータ

### 2.2 APKダウンロード

```
GET {serverUrl}/api/player/update/download?key={client_key}
```

**レスポンス:** `Content-Type: application/vnd.android.package-archive`、BodyはAPKバイナリ。

### 2.3 サーバー側のファイル配置（version.json方式）

サーバーは管理ファイル `version.json` を読んでチェックAPIのレスポンスを生成し、
ダウンロードAPIは隣のAPKをそのまま返す構成：

```
release/（またはuploads/{app_id}/）
├── signage-android-debug.apk   ← 配信するAPK
└── version.json                ← 2.1のレスポンスと同形式
```

**リリース時はAPK差し替えと `version.json` の `version_code`/`version_name` 更新をセットで行う。**

## 3. クライアント実装（Kotlin / OkHttp / Gson）

以下、`{applicationId}` は新アプリのパッケージ名に読み替え。
依存: `okhttp`, `gson`, `kotlinx-coroutines`, `androidx.core`（FileProvider）。

### 3.1 データクラス

```kotlin
data class UpdateInfo(
    @SerializedName("version_code") val versionCode: Int,
    @SerializedName("version_name") val versionName: String,
    @SerializedName("url") val url: String,
    @SerializedName("force") val force: Boolean = false
)
```

### 3.2 サーバー通信（ServerClient相当）

```kotlin
class ServerClient(private val serverUrl: String, private val clientKey: String) {

    private val gson = Gson()
    private val client = OkHttpClient.Builder()
        .connectTimeout(30, TimeUnit.SECONDS)
        .readTimeout(30, TimeUnit.SECONDS)
        .build()
    // ※社内プロキシ経由が必要な環境は §8 参照

    private fun buildUrl(endpoint: String): String =
        "$serverUrl$endpoint${if (endpoint.contains("?")) "&" else "?"}key=$clientKey"

    /** アップデートチェック。失敗時はnull（致命的でないため握りつぶす） */
    suspend fun checkForUpdate(): UpdateInfo? = withContext(Dispatchers.IO) {
        try {
            val url = buildUrl("/api/player/update/check")
            val request = Request.Builder().url(url).get().build()
            client.newCall(request).execute().use { resp ->
                if (resp.isSuccessful) {
                    val body = resp.body?.string() ?: return@withContext null
                    gson.fromJson(body, UpdateInfo::class.java)
                } else null
            }
        } catch (e: Exception) { null }
    }

    /**
     * APKダウンロード。サーバーが返す url の3形式に対応:
     *  1. 絶対URL (http...)            → そのまま使用
     *  2. key= を含むフルパス          → serverUrlのhost:portのみ結合（パス二重化防止）
     *  3. 相対パス                     → serverUrl結合 + key付与
     */
    suspend fun downloadApk(downloadPath: String, destFile: File): Boolean =
        withContext(Dispatchers.IO) {
            try {
                val url = if (downloadPath.startsWith("http")) {
                    downloadPath
                } else if (downloadPath.contains("key=")) {
                    val uri = URI(serverUrl)
                    val baseHost = "${uri.scheme}://${uri.host}" +
                        if (uri.port > 0) ":${uri.port}" else ""
                    "$baseHost$downloadPath"
                } else {
                    buildUrl(downloadPath)
                }
                val request = Request.Builder().url(url).get().build()
                client.newCall(request).execute().use { resp ->
                    if (resp.isSuccessful) {
                        resp.body?.byteStream()?.use { input ->
                            FileOutputStream(destFile).use { output -> input.copyTo(output) }
                        }
                        true
                    } else false
                }
            } catch (e: Exception) { false }
        }
}
```

### 3.3 アップデートマネージャ（AppUpdateManager相当）

```kotlin
class AppUpdateManager(
    private val context: Context,
    private val serverClient: ServerClient,
    private val onLog: (String) -> Unit = {}
) {
    companion object { private const val APK_FILENAME = "app-update.apk" }

    private val apkDir = File(context.filesDir, "updates").apply { if (!exists()) mkdirs() }
    private val apkFile = File(apkDir, APK_FILENAME)

    /** 自分のversionCodeを取得（API互換対応込み） */
    fun getCurrentVersionCode(): Int = try {
        val pi = if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU) {
            context.packageManager.getPackageInfo(
                context.packageName, PackageManager.PackageInfoFlags.of(0))
        } else {
            @Suppress("DEPRECATION")
            context.packageManager.getPackageInfo(context.packageName, 0)
        }
        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.P) pi.longVersionCode.toInt()
        else @Suppress("DEPRECATION") pi.versionCode
    } catch (e: Exception) { 0 }

    /** チェック→DL→インストール起動の一連処理。更新を開始したらtrue */
    suspend fun checkAndUpdate(): Boolean {
        val updateInfo = serverClient.checkForUpdate() ?: run {
            onLog("サーバー応答なし"); return false
        }
        val currentVersion = getCurrentVersionCode()
        onLog("現在v$currentVersion → サーバーv${updateInfo.versionCode}")

        if (updateInfo.versionCode <= currentVersion) {
            if (apkFile.exists()) apkFile.delete()  // 古いDL残骸を掃除
            return false
        }

        if (!serverClient.downloadApk(updateInfo.url, apkFile) || !apkFile.exists()) {
            onLog("ダウンロード失敗"); return false
        }
        onLog("ダウンロード完了 (${apkFile.length() / 1024 / 1024}MB)")

        triggerInstallViaIntent()
        return true
    }

    /** ACTION_VIEW Intent方式でインストーラー起動（実運用方式） */
    private fun triggerInstallViaIntent() {
        try {
            val apkUri = FileProvider.getUriForFile(
                context, "${context.packageName}.fileprovider", apkFile)
            val installIntent = Intent(Intent.ACTION_VIEW).apply {
                setDataAndType(apkUri, "application/vnd.android.package-archive")
                addFlags(Intent.FLAG_GRANT_READ_URI_PERMISSION)
                addFlags(Intent.FLAG_ACTIVITY_NEW_TASK)
            }
            context.startActivity(installIntent)
        } catch (e: Exception) {
            onLog("インストーラー起動失敗: ${e.message}")
        }
    }
}
```

### 3.4 定期チェックループ（Foreground Service内）

signageでは常駐Foreground Service（`foregroundServiceType="dataSync"`）のコルーチンで実行：

```kotlin
private const val UPDATE_CHECK_INTERVAL_MS = 60_000L  // 1分間隔（アプリ要件に応じ調整）

updateCheckJob = coroutineScope.launch {       // CoroutineScope(Dispatchers.IO + SupervisorJob())
    val updateManager = AppUpdateManager(context, serverClient) { msg -> log(msg) }
    delay(10_000)                               // 起動10秒後に初回チェック
    while (isActive) {
        try { updateManager.checkAndUpdate() } catch (e: Exception) { log("チェック失敗: ${e.message}") }
        delay(UPDATE_CHECK_INTERVAL_MS)
    }
}
```

- 常駐サービスがないアプリなら WorkManager の PeriodicWorkRequest（最短15分間隔）でも代替可。
- 1分間隔は「リリース後すぐ反映させたい」運用要件のため。負荷的にはレスポンスが小さいので問題なし。

## 4. AndroidManifest 必須項目

```xml
<!-- 権限 -->
<uses-permission android:name="android.permission.INTERNET" />
<uses-permission android:name="android.permission.REQUEST_INSTALL_PACKAGES" />
<!-- Foreground Serviceでループを回す場合は追加で -->
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_DATA_SYNC" />

<application ... android:usesCleartextTraffic="true">  <!-- サーバーがhttpの場合に必要 -->

    <!-- DL済みAPKをインストーラーに渡すためのFileProvider -->
    <provider
        android:name="androidx.core.content.FileProvider"
        android:authorities="${applicationId}.fileprovider"
        android:exported="false"
        android:grantUriPermissions="true">
        <meta-data
            android:name="android.support.FILE_PROVIDER_PATHS"
            android:resource="@xml/file_paths" />
    </provider>
</application>
```

### res/xml/file_paths.xml

```xml
<?xml version="1.0" encoding="utf-8"?>
<paths>
    <files-path name="updates" path="updates/" />
</paths>
```

> `files-path` は `context.filesDir` 配下を指す。`File(context.filesDir, "updates")` と対応。

### 端末側の初回設定

非Device Owner端末では、初回更新時に「提供元不明アプリのインストール許可」を
このアプリに対して有効化する必要がある（設定 → アプリ → 特別なアプリアクセス →
不明なアプリのインストール）。一度許可すれば以降は確認画面のみ。

## 5. ユーザー体験（Intent方式の挙動）

1. 更新検知 → ダウンロード（バックグラウンド、画面はそのまま）
2. インストーラーが前面に出る（白い確認画面）
3. 「インストール」タップ → 進行 → 完了画面
4. 「開く」タップでアプリ再起動

※キオスク端末で完全無人化したい場合は §7 のSession API + Device Owner が必要。

---

## 6. リリース手順（アプリ側）

1. `app/build.gradle.kts` の `versionCode` と `versionName` をインクリメント
2. ビルドしてAPK生成
3. サーバーの配信ディレクトリへAPKを配置し、`version.json` の
   `version_code` / `version_name` を **build.gradle.kts と同じ値** に更新
4. 端末は次のチェック周期（最大1分）で自動更新

> versionCode の不一致（APKは新しいのにversion.jsonが古い等）は更新ループや
> 無限再DLの原因になるため、必ずセットで更新する。

## 7. （オプション）Session API によるサイレント更新

`PackageInstaller.Session` でAPKを書き込み `session.commit()` する方式。

- **Device Owner設定済み端末**（または同一署名のAndroid 12+の自己更新）ではサイレント更新可
- 非Device Owner端末では `STATUS_PENDING_USER_ACTION` が `BroadcastReceiver` に届くので
  `EXTRA_INTENT` の確認画面を起動する必要がある
- **signageでの実績**: 非Device Owner端末でcommit直後にアプリがkillされ、確認画面に
  到達できないケースがあったため **Intent方式に切り替えた**。Device Owner運用が
  確実な場合のみ採用を推奨

採用する場合は結果受信用Receiverをマニフェスト登録する：

```xml
<receiver android:name=".InstallResultReceiver" android:exported="false">
    <intent-filter>
        <action android:name="{applicationId}.INSTALL_RESULT" />
    </intent-filter>
</receiver>
```

Receiver側では `STATUS_SUCCESS` 受信時に
`packageManager.getLaunchIntentForPackage(packageName)` で自動再起動できる
（サイレント更新時の自動復帰）。

## 8. 環境依存・移植時の調整リスト

| 項目 | signageでの値 | 新アプリでの対応 |
|------|--------------|----------------|
| パッケージ名 | `jp.co.tisa.signage_android` | `{applicationId}` に置換 |
| FileProvider authority | `${applicationId}.fileprovider` | そのままでOK（applicationId連動） |
| サーバーURL / client_key | 初回設定画面でSharedPreferencesに保存 | 新アプリの設定方法に合わせる |
| **APKスロット** | `/api/player/update/*`（signage専用） | **必ず別スロットに**（§2冒頭） |
| 社内プロキシ | OkHttpに `210.175.128.100:8080` を設定し、ローカルIP/`atg.co.jp` はバイパス（プレフィックス一致で direct/proxy クライアントを切替） | サーバーが社内のみなら不要。外部URL併用なら同様のバイパス実装を移植 |
| チェック間隔 | 起動10秒後 + 60秒間隔 | 要件に応じ調整（WorkManagerなら最短15分） |
| cleartext通信 | `usesCleartextTraffic="true"`（http運用） | httpsならば不要 |

## 9. サーバー担当への依頼文テンプレ（APKスロット分離）

```
別アプリ（{app_id}）でも既存のOTA更新APIを使いたいので、APKスロットの分離をお願いします。

1. GET /api/player/update/check?key=...&app={app_id}
   → uploads/{app_id}/version.json の内容を返す（appパラメータ未指定時は従来通りsignage）
2. GET /api/player/update/download?key=...&app={app_id}
   → uploads/{app_id}/ 配下のAPKを返す

version.json / レスポンス形式は現行と同一です。
```

> クライアント側は §3.2 の `buildUrl("/api/player/update/check?app={app_id}")` のように
> エンドポイント文字列に `?app=` を含めるだけで対応可能（`buildUrl` が `&key=` を付与する）。
